# 视障用户操作原理与「眼睛-手」完善方案

> 研究视障用户如何通过听觉反馈操作电脑，并将该原理融入 SuperOS 的「眼睛」（感知）与「手」（动作）能力。  
> 更新于 2026-03-15

---

## 一、视障用户操作原理

### 1.1 核心机制

视障用户使用**读屏软件**（Windows 讲述人/Narrator、NVDA、JAWS 等）配合**键盘导航**操作电脑：

| 步骤 | 用户动作 | 系统反馈 |
|------|----------|----------|
| 1 | 按 **Tab** 或方向键 | 焦点移动到下一个可交互元素 |
| 2 | 读屏软件监听焦点变化 | 调用 `IUIAutomation::GetFocusedElement` 获取当前焦点元素 |
| 3 | 读取元素属性 | `Name`、`ControlType`、`LocalizedControlType` 等 |
| 4 | 语音播报 | 告知用户「按钮，开始创作」「编辑框，文件名」等 |
| 5 | 用户决策 | 若为目标则 Enter/空格执行，否则继续 Tab |

**本质**：**导航 → 感知反馈 → 决策 → 动作** 的闭环。用户不需要「看见」屏幕，通过**结构化反馈**得知当前焦点是什么。

### 1.2 技术栈（Windows）

- **UI Automation (UIA)**：暴露无障碍树，供读屏软件消费
- **GetFocusedElement**：获取当前焦点元素
- **Tab 顺序**：应用定义的可焦点元素遍历顺序（通常与视觉布局相关）
- **Invoke 模式**：按钮等控件支持 `InvokePattern.Invoke()`，等效于点击

## 二、与 SuperOS 的映射

### 2.1 当前「眼睛」能力

| 能力 | 实现 | 局限性 |
|------|------|--------|
| 按名称查找 | UiaSniper / FindAll | 中文编码、部分应用不暴露 Name |
| 树遍历 | getGlobalSnapshot、TreeWalker | 元素过多、结构复杂时噪音大 |
| 坐标 | 固定 (x,y) 比例 | UI 改版即失效，无反馈 |

### 2.2 当前「手」能力

| 能力 | 实现 | 局限性 |
|------|------|--------|
| 点击 | clickByName、坐标 | 无点击后验证 |
| 输入 | typeText | 无聚焦验证 |
| 快捷键 | sendKeys | 依赖窗口已激活 |

### 2.3 借鉴视障原理的改进

| 视障机制 | 我们的实现 |
|----------|------------|
| Tab + GetFocusedElement | **Tab 序扫描**：对目标窗口 sendKeys Tab，每次后调用 GetFocusedElement，收集 `{name, rect, controlType}`，形成「用户视角下的元素列表」 |
| 语音反馈 | **结构化反馈**：返回元素列表供 clickByName 匹配，或供 LLM 推理下一步 |
| 确认后动作 | **动作后验证**：点击后可选检查 FocusedElement 是否为预期，或目标元素状态变化 |
| 多次 Tab 探索 | **重试时换策略**：首次坐标失败时，尝试 Tab 扫描找到等价元素再 Invoke |

## 三、实现方案

### 3.1 「眼睛」完善：Tab 序扫描

**新增** `enumerateFocusableByTabOrder(hwnd, maxTabs?)`：

1. `bringWindowToFront(hwnd)` 确保窗口激活
2. 循环最多 `maxTabs` 次（如 50）：
   - `sendKeys("{TAB}")`
   - `delay(80)` 等待焦点稳定
   - 调用 PowerShell 获取 `AutomationElement.FocusedElement`
   - 若焦点在目标 hwnd 内，提取 `Name`、`BoundingRectangle`、`ControlType`
   - 加入列表，避免重复（同一元素可能因循环回到）
3. 返回 `Array<{ name, rect, controlType, tabIndex }>`

**用途**：
- 当 `clickByName` 的 UIA 查找失败时，先 Tab 扫描，在结果中按 name 模糊匹配，取 rect 中心点击
- 或对匹配元素使用 `InvokePattern.Invoke()`（若可用）

### 3.2 「手」完善：动作后验证

**可选** 在 `clickByName` 成功后：
- 若目标为按钮，可再读一次 FocusedElement 或目标元素 IsInvokePatternAvailable，确认点击生效
- 若为编辑框聚焦，可确认 FocusedElement 的 ControlType 为 Edit

**当前优先级**：较低，先完成「眼睛」的 Tab 扫描。

### 3.3 与现有能力的整合

```
clickByName 新流程（可选启用）：
  Name 查找 (UiaSniper) → 失败
  → SuperEye (若有) → 失败
  → 坐标兜底 (若有应用专用坐标) → 失败
  → 【新增】Tab 序扫描 → 在结果中匹配 name → Invoke 或 坐标点击
  → 失败则抛错
```

## 四、依赖与约束

- **Tab 会改变焦点**：扫描前需确保目标窗口激活；扫描后焦点在最后一个元素，可能影响后续步骤
- **循环检测**：Tab 序可能形成循环，需记录已访问元素，避免无限循环
- **性能**：每次 Tab + 取焦点约 100–200ms，50 次约 5–10s，仅作兜底
- **编码**：PowerShell 调用 .NET UIA 时注意 UTF-8，与现有 directShellBridge 一致
