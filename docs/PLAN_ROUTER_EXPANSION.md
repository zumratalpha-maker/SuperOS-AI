# 意图路由扩展计划：放宽限制、支持更多操作场景

## 问题

用户输入「现在打开我的微信，给阿尔法发微信暧昧一下」时，被分类为 **CHAT**，直接返回帮助文案，未尝试执行。

**根本原因**：当前分类提示词和关键词过于保守，把「举例」当成了「限定范围」。

---

## 现状分析

| 环节 | 当前逻辑 | 问题 |
|------|----------|------|
| **分类提示** | COMPLEX 需同时有「打开」+「写/输入/保存/点击/点/另存为」 | 「发」「发微信」「发消息」未覆盖 |
| **复合关键词** | `["写","输入","保存","点击","点","另存为","打字","写入","到桌面"]` | 缺「发」「发送」「回复」「留言」等 |
| **CHAT 定义** | 闲聊、打招呼、问你能做什么、无关对话 | 边界模糊，易把「打开+发消息」误判为闲聊 |
| **帮助文案** | 列举「打开、多步、资源猎人…」 | 像能力边界，实际只是示例 |

---

## 改进计划

### 1. 扩展复合动作关键词（parseIntent.ts）

**变更**：在 `COMPOUND_ACTION_KEYWORDS` 中新增：
- `发`、`发送`、`发微信`、`发消息`、`回复`、`留言`、`发给`、`发給`

**效果**：「打开微信给阿尔法发微信」会命中关键词，强制走 `COMPLEX_A11Y_PLANNING`。

---

### 2. 收紧 CHAT 定义（hybridRouter.ts）

**变更**：调整 `LOCAL_CLASSIFY_PROMPT` 中 CHAT 的说明：

**原**：
```
CHAT：闲聊、打招呼、问你能做什么、无关对话
```

**新**：
```
CHAT：仅限纯闲聊——如「你好」「在吗」「你能做什么」「今天天气怎样」，且句中没有「打开/发/写/点/发消息」等操作意图。一旦有明确动作（打开某应用、发消息给某人、写X、点X），必须标 COMPLEX 或 SIMPLE，不得标 CHAT。
```

**效果**：减少「打开 + 发消息」被误判为 CHAT 的概率。

---

### 3. 补充 COMPLEX 示例（hybridRouter.ts）

**变更**：在分类提示中增加社交类示例：

```
例如：打开记事本写诗、打开微信给某人发消息、打开X输入Y保存、打开X点文件保存。
```

**效果**：模型更容易把「打开微信 + 发消息」归类为 COMPLEX。

---

### 4. 优化帮助文案（jarvis.ts）

**变更**：避免列举式限制感，改为开放式引导：

**原**：
```
当前支持：打开任意已注册目标；多步指令；资源猎人…你好/ni hao 显示本帮助。
```

**新**：
```
示例：打开应用、多步操作（如打开记事本写诗保存）、资源搜索、自主研究等。你好/ni hao 显示本帮助。你可用自然语言描述想做的事，我会尽量执行。
```

**效果**：明确这是「示例」而非「能力边界」。

---

### 5. 云端/本地规划对「发消息」的支持

**说明**：微信这类应用需通过 A11y/UI 树完成：打开微信 → 点击联系人 → 输入并发送。  
`planWithCloud` / `planWithLocal` 已支持 `open_app` + `click` + `type` 组合，无需改规划逻辑，只需保证该类指令被正确路由到 COMPLEX。

---

## 预期效果

- 「打开微信，给阿尔法发微信暧昧一下」→ 走 `COMPLEX_A11Y_PLANNING` → 尝试生成并执行步骤  
- 纯闲聊（你好、在吗）→ 仍为 CHAT，显示帮助  
- 其他「打开 + 发/写/点」类指令 → 优先走 COMPLEX，减少误判为 CHAT
