# 微信发消息流程问题 — 完整排查方案

## 一、现象

- **表现**：执行「打开微信阿尔法发消息说 我现在很忙」时，停在「第 1/7 步: open_app 微信」，无后续输出，最终 90s 超时。
- **历史**：最初能搜到联系人（Ctrl+F → type 阿尔法 → Enter），但点不到输入框输入；经多次修改后反而卡在 open_app，无法继续。

---

## 二、执行链路梳理

### 2.1 open_app 微信 的完整流程

```
executeOneStep(open_app 微信)
  ├─ resolveAndLaunch("微信")        ← 可能瓶颈 1
  ├─ delay(2500ms)                    ← 固定 2.5s
  ├─ findWindowByAppWithRetry(...)   ← 可能瓶颈 2
  ├─ bringWindowToFront(...)
  └─ return next
```

整条 a11y 链被 `withTimeout(90000)` 包裹，即**所有 7 步共享 90 秒**。

### 2.2 后续步骤（当前未执行到）

2. keys ^f  
3. type 阿尔法  
4. keys Enter  
5. click 输入 (focusWeChatInputBox)  
6. type 我现在很忙  
7. keys Enter  

---

## 三、根因分析

### 3.1 瓶颈 1：resolveAndLaunch 的桌面扫描

**位置**：`appExecutor.ts` → `resolveAndLaunch` → `resolveDesktopShortcut`

**逻辑**：
1. 先执行 `resolveDesktopShortcut(name)`，扫描桌面所有 `.lnk` 文件
2. 对**每个** `.lnk` 调用 `resolveLnkTarget(fullPath)`，内部 spawn PowerShell
3. 只有桌面未命中时，才走到 appRegistry 的 `D:\weixin\Weixin.exe`

**耗时估算**：
- 桌面若有 30 个快捷方式，每个解析约 1–3s
- 总耗时约 **30–90 秒**，足以接近或吃满 90s 总超时

**结论**：appRegistry 已配置微信路径时，仍被强制先做全桌面扫描，是明显瓶颈。

---

### 3.2 瓶颈 2：findWindowByAppWithRetry 查窗过慢

**位置**：`runA11ySequence.ts` → `findWindowByAppWithRetry`  
**条件**：`USE_SUPEREYE` 未设置时走 PowerShell 路径

**逻辑**：
- 微信：12 次重试，每次间隔 220ms
- 每次尝试名称：`[微信, WeChat, wechat]`
- 每次 `findWindowByName`：
  - `runFindWindowFromRoot`：UIA `RootElement.FindAll`，spawn PowerShell，**单次超时 12s**
  - 失败时再 `runFindWindowByProcessName`：同样 UIA，**单次超时 12s**

**耗时估算**（极端情况）：
- 12 次 × 3 个名称 × 12s ≈ 432s
- 受总 90s 限制，实际可能只完成 2–3 轮尝试即超时

**结论**：UIA 查窗单次 12s 过长，且重试策略在 90s 内难以完成足够次数。

---

### 3.3 其他问题

1. **fixWeChatOpenAppStep 日志**：`"[object Object]"` 说明打印了整对象而非 `step.app`
2. **SuperEye**：若 `USE_SUPEREYE=1` 且 supereye.exe 异常，会触发 20s RPC 超时后 fallback，这部分相对可控

---

## 四、解决方案（按优先级）

### 方案 A：resolveAndLaunch 优先使用 appRegistry（高优先级）

**目标**：对已配置的本地 exe，若路径存在，直接启动，跳过桌面扫描。

**做法**：
- 在 `resolveAndLaunch` 中，在「桌面快捷方式」之前增加分支：
- 若 `expandedFromRegistry` 为本地路径（非 URL、非系统命令）且 `fs.existsSync(presetPath)` 为 true
- 则直接 `launchByPath` 并返回，不调用 `resolveDesktopShortcut`

**效果**：微信路径在 appRegistry 且存在时，启动时间从几十秒降到秒级。

---

### 方案 B：微信查窗优化（高优先级）

**目标**：缩短查窗时间，提高在 90s 内成功的概率。

**做法 1**：微信优先按进程名查窗  
- 对 `微信/WeChat/wechat`，先调用 `runFindWindowByProcessName("WeChat")`
- 该路径不依赖窗口标题，只依赖进程名，通常比 UIA 全量扫描快
- 失败后再用 `runFindWindowFromRoot` 兜底

**做法 2**：缩短 UIA 超时  
- 将 `runFindWindowFromRoot` 的 `UIA_SCRIPT_TIMEOUT_MS` 从 12000 降到 6000  
- 或为查窗单独设更低超时（如 5000），避免单次卡太久

**做法 3**：减少重试次数  
- 微信的 `maxAttempts` 从 12 降到 6，间隔保持 220ms  
- 在 90s 内可以完成更多「有效尝试」

---

### 方案 C：为 open_app 单独设超时（中优先级）

**目标**：避免 open_app 占满整链 90s，后续步骤仍有时间执行。

**做法**：
- 在 `a11ySequenceStep` 中，对 `open_app` 步骤用 `withTimeout(30000)` 包一层
- 超时后抛错，由已有重试逻辑处理，或给出明确提示

---

### 方案 D：小修复

1. **fixWeChatOpenAppStep 日志**：改为 `console.log(..., (s as any).app)`，避免 `[object Object]`
2. **resolveDesktopShortcuts 限流**：若必须保留桌面扫描，可限制最多解析 10 个 `.lnk`，或为每次 `resolveLnkTarget` 加 2s 超时

---

## 五、推荐实施顺序

1. **方案 A**：优先完成，对已配置 appRegistry 的应用影响最大，预计解决主要卡顿。
2. **方案 B 做法 1**：微信查窗优先进程名，提升查窗成功率。
3. **方案 D.1**：修正 fixWeChatOpenAppStep 日志。
4. 视测试结果再考虑方案 B.2/B.3、方案 C。

---

## 六、验证方式

执行 `打开微信阿尔法发消息说 我现在很忙` 后，预期：

1. 2–3 秒内完成微信启动；
2. 5–15 秒内完成查窗；
3. 终端出现 `第 2/7 步`、`第 3/7 步` 等日志；
4. 最终进入 `click 输入`、`type 我现在很忙`、`keys Enter`。

若仍卡在 `第 1/7 步`，可分别在 `resolveAndLaunch` 前后和 `findWindowByAppWithRetry` 前后加 `console.log` 粗粒度计时，定位具体卡点。
