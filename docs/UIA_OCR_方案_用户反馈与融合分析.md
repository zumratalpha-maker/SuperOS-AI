# UIA + OCR 双引擎方案：用户反馈综合分析与融合

> 对用户提出的 4 点优化进行逐条分析，取长补短，形成融合方案。  
> 更新于 2026-03

---

## 一、你的想法逐条分析

### 1. 「UIA 失效应用」动态判断，而非写死

**你的想法**：不做硬编码名单（微信、剪映），新增「UIA 有效性检测」；若连续 2 次 UIA 查找失败 → 自动标记该应用为「OCR 优先」，飞书、钉钉等新 Electron 应用自动适配。

| 维度 | 分析 |
|------|------|
| **方向** | ✅ **正确**。动态检测比维护名单更通用。 |
| **实现要点** | 需明确「失败」的粒度：按**应用**统计，不按单次 target。 |
| **风险** | 「连续 2 次」可能过敏感：首次失败可能只是时序问题，第二次就切到 OCR 会过早放弃 UIA。 |
| **建议** | 改为 **「近 N 次尝试中失败率 ≥ 阈值」**：例如近 5 次 UIA 尝试中 ≥4 次失败 → 标记该应用为 OCR 优先。或：连续 3 次失败再标记，降低误判。 |
| **存储** | 内存缓存 `Map<appKey, { attempts, failures }>`，进程内有效；可选持久化到 `data/uia_failure_cache.json` 供下次启动复用。 |

**融合结论**：采纳动态判断，用「失败率 + 时间窗口」代替「连续 2 次」；与现有 `automation_success_cache` 对称设计 `uia_failure_cache`。

---

### 2. OCR 区域截图，而非全屏

**你的想法**：不截全屏，按任务只截「局部区域」——微信输入框只截聊天下半部分，浏览器只截地址栏；先 UIA 取窗口坐标 → 裁剪目标区域 → OCR，速度提升 3–5 倍，减少误识别。

| 维度 | 分析 |
|------|------|
| **方向** | ✅ **正确**。区域截图是业界通用做法（SikuliX Region、UiPath Region）。 |
| **实现难点** | 「通过 UIA 获取目标区域」——在微信等 UIA 失效场景下，UIA 拿不到子控件 rect。 |
| **解决** | **双路径**：<br>• 有 UIA 时：用元素 BoundingRectangle 作为区域<br>• 无 UIA 时：用「**应用 + 任务 → 区域模板**」，如 微信\|输入框 → 窗口下半 25% `(0, 0.75, 1, 1)`<br>窗口 rect 本身可通过 `GetWindowRect` 获取，不依赖 UIA。 |
| **区域模板** | 配置化，如 `{ "微信|输入框": [0, 0.75, 1, 1], "微信|发送": [0.85, 0.9, 1, 1], "浏览器|地址栏": [0, 0, 1, 0.08] }`，单位为相对比例。 |
| **收益** | 截图面积减小 → OCR 更快、候选更少、误匹配率降低。 |

**融合结论**：采纳区域截图；区域来源 = UIA（优先）+ 区域模板（UIA 失效时）；与现有「按 hwnd 截窗口」兼容。

### 3. learned_actions 过期 / 失效自动剔除

**你的想法**：学习坐标易因软件更新、窗口变化失效；加「有效期」（如 7 天）或「失效检测」：执行后校验是否达到预期，失败则弃用并切 OCR 重新定位，实现自修复。

| 维度 | 分析 |
|------|------|
| **方向** | ✅ **正确**。坐标会随时间失效，需要自愈。 |
| **固定 7 天** | ⚠️ **不推荐**。7 天后仍有可能是有效的，按时间一刀切会误删。 |
| **更好的方式** | **按失败次数失效**：同一 target 的 learned 坐标，若连续失败 N 次（如 2）→ 标记失效并从 learned_actions 移除（或标记 `invalid: true`）；下次执行时跳过，直接走 OCR；若 OCR 成功，可再写回 learned 作为新样本。 |
| **「预期效果」校验** | 理想但实现复杂。例如「点击输入框后是否激活输入」——微信 UIA 不完整，难以通用检测。可简化为：<br>• 执行 learned 点击后，若**下一步**（如 type）明确失败（超时、无反应）→ 回溯认为本次 click 无效，计入失败<br>• 或：点击后延迟 200ms，再截区域 OCR 检查是否出现期望变化（如「发送」按钮由灰变亮）——复杂度较高，可作为 Phase 2 |
| **最小可行** | 先做「失败即弃用」：若 learned 坐标点击后，同一流程的后续步骤失败且可归因于「没点中」，则弃用该条 learned。 |

**融合结论**：采纳「失败驱动失效」，不采用固定 7 天；先实现「连续失败 N 次 → 弃用」，后续可迭代「预期效果」校验。

### 4. OCR 模糊匹配 + 优先级 + 图标兜底

**你的想法**：避免 OCR 识别偏差，加模糊匹配（搜「发送」可匹配「发」「发送」「send」）；对常见控件设文字优先级（输入框优先「输入」「请输入」）；对无文字按钮（如微信发送箭头）用轻量图像模板匹配兜底。

| 维度 | 分析 |
|------|------|
| **模糊匹配** | ✅ **必须**。OCR 常有错字、漏字，如「发迭」「送」等。可用：<br>• 包含关系：目标词包含关键词即命中<br>• 编辑距离（Levenshtein）：容错 1–2 字<br>• 同义/别名表：发送 ≈ 发送消息 ≈ Send |
| **优先级** | ✅ **有价值**。多候选时按控件类型和任务选优：输入框偏下、发送偏右下；或显式优先级表。 |
| **图标兜底** | ✅ **正确方向**，但实现成本较高。需要：<br>• 模板图库（发送箭头、关闭、最大化等）<br>• OpenCV `matchTemplate` 或类似<br>• 与文字 OCR 的切换逻辑<br>建议作为 **Phase 2**，Phase 1 先做好文字 OCR + 模糊匹配 + 优先级。 |

**融合结论**：采纳模糊匹配和优先级；图标兜底列入 Phase 2，文字 OCR 稳定后再扩展。

## 二、融合后的整体架构（更新版）

```
┌─────────────────────────────────────────────────────────────────────┐
│                    clickByName / 定位入口                              │
└─────────────────────────────────────────────────────────────────────┘
    │
    ├─ 1. 语义快捷键 ──有──▶ sendKeys，返回
    ├─ 2. 用户教学 / 成功缓存 ──有且未失效──▶ 坐标点击，返回
    │         │
    │         └─ 若点击后流程失败 ──▶ 标记失效，从 learned 移除
    │
    ├─ 3. 应用专用坐标（剪映等）──有──▶ 坐标点击，返回
    │
    ├─ 4. UIA 有效性检查（新增）
    │         │
    │         ├─ 该应用已标记「OCR 优先」？ ──是──▶ 跳过 UIA，直接 6
    │         │
    │         └─ 否 ──▶ 执行 UIA 查找
    │                   ├─ 成功 ──▶ 点击，返回；记录成功（可刷新失败计数）
    │                   └─ 失败 ──▶ 更新失败计数；若 近N次≥阈值 ──▶ 标记「OCR 优先」
    │
    ├─ 5. （可选）Tab 扫描兜底 ──失败──┐
    │                                  │
    └──────────────────────────────────┘
                                       ▼
    ┌──────────────────────────────────────────────────────────────────┐
    │ 6. OCR 引擎（新增）                                                │
    │    ├─ 取目标窗口 hwnd、GetWindowRect                              │
    │    ├─ 按「应用|任务」取区域模板 → 裁剪区域 bitmap（非全屏）        │
    │    ├─ Windows.Media.Ocr 识别 → [{text, bbox}]                     │
    │    ├─ 模糊匹配 + 优先级排序 → 选最佳候选                           │
    │    └─ clickAt(bbox 中心)                                          │
    │    │                                                               │
    │    └─ （Phase 2）无文字候选 → 图像模板匹配兜底                      │
    └──────────────────────────────────────────────────────────────────┘
```

## 三、数据流与缓存设计

| 缓存 | 用途 | 更新策略 |
|------|------|----------|
| `automation_success_cache` | 记录「哪种策略成功了」 | 成功时写入，用于下次优先 |
| `uia_failure_cache`（新增） | 记录「某应用 UIA 是否优先」 | 失败率超阈值时标记 OCR 优先；成功时可降权或清除 |
| `learned_actions` | 用户教学坐标 | 失败时移除或标记 invalid |
| `region_templates`（新增） | 应用+任务 → 截图区域比例 | 配置化，可按应用迭代 |

## 四、取长补短总结

| 你的想法 | 结论 | 细化 |
|----------|------|------|
| 1. 动态 UIA 失效判断 | ✅ 采纳 | 用「失败率 / 连续次数」代替固定名单 |
| 2. 区域截图 OCR | ✅ 采纳 | UIA rect + 区域模板双路径 |
| 3. learned 过期/失效 | ✅ 采纳 | 失败驱动失效，不做固定 7 天 |
| 4. 模糊匹配+优先级+图标 | ✅ 采纳前二；图标 Phase 2 | 优先做好文字 OCR 鲁棒性 |

## 五、与原有方案的关系

- 原有：UIA 优先 + 坐标兜底 + Tab 兜底，无 OCR。
- 融合后：在原有链路上增加 **动态 UIA 有效性**、**OCR 兜底**、**learned 自愈**、**区域 OCR**，形成闭环。
- 收益：通用性更强、维护成本更低、新 Electron 应用自动适配、教学坐标具备自修复能力。
